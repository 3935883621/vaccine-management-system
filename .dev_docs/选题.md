# 疫苗管理系统 — 数据库系统设计选题说明

---

## 一、选题内容与适用场景

### 选题名称

**疫苗管理系统**

### 选题描述

本系统是一个面向疫苗从生产到接种全链路管理的数据库系统。系统围绕 **"用户选择要接种的疫苗 → 选择接种机构 → 选择护士班次"** 这一核心流程展开，覆盖接种机构对护士与班次的管理、疫苗的入库存储管理，以及与疫苗工业生产商的供货对接。

### 适用场景

本系统用于解决以下真实痛点问题：

- **用户接种选择困难**：用户需要查看有哪些疫苗可接种、哪些机构有苗、哪个时段有位，缺乏统一的信息查询与预约入口。
- **机构排班与库存脱节**：接种机构的护士班次安排与疫苗库存之间缺乏联动，容易出现"有位无苗"或"有苗无人"的资源错配。
- **供应链信息不透明**：疫苗从哪个生产商生产、哪个批次、何时配送到哪个机构，信息分散难以追溯，影响接种安全。

本系统通过一套统一的数据库结构，将 **生产商供货 → 机构入库存储 → 用户选择预约 → 护士执行接种** 四个环节串联起来，确保每一支疫苗的来源可查、去向可追。

---

## 二、角色与功能结构

本系统涉及 **3 个角色**，各角色的功能结构如下：

### 角色 1：接种用户（居民）

接种用户是需要接种疫苗的居民，系统从用户的视角出发，提供以下功能：

| 功能模块 | 功能说明 |
|---|---|
| 浏览疫苗信息 | 查看当前可接种的疫苗种类、适用人群、接种说明等基本信息 |
| 查询机构信息 | 按地区或名称查找接种机构，查看该机构当前可用的疫苗品种及库存余量 |
| 选择护士班次 | 在目标机构中选择可用的护士班次（时段），每个班次有剩余可预约名额限制 |
| 提交预约申请 | 确认疫苗、机构、班次后提交预约，系统校验库存充足后生成预约记录 |
| 查看预约状态 | 查看自己预约的当前状态（待接种 / 已完成 / 已取消） |
| 查看接种记录 | 接种完成后查看接种详情，包括所用疫苗名称、批次编号、接种护士、接种时间等 |

**用户视角的核心流程**：用户先选择想要接种的 **疫苗**，然后选择提供该疫苗的 **接种机构**，再在该机构中选择一个可用的 **护士班次（时段）**，系统确认该机构对应疫苗库存充足后完成预约。

---

### 角色 2：机构管理员（接种机构）

机构管理员负责管理接种机构的日常运营，包括护士排班和疫苗库存管理：

| 功能模块 | 功能说明 |
|---|---|
| 管理护士信息 | 录入、修改、删除本机构的护士信息（姓名、工号、职称等） |
| 管理护士班次 | 为护士创建排班计划，设置每个班次的日期、时段（如 08:00–12:00）、最大可预约人数；用户预约时占用名额，取消时释放名额 |
| 管理疫苗库存 | 查看本机构当前各疫苗的库存数量、批次信息、有效期；当库存不足或临期时进行预警提示 |
| 处理疫苗入库 | 接收生产商配送的疫苗后，登记入库信息：关联疫苗品种、生产商、批次号、数量、有效期，库存相应增加 |
| 处理预约请求 | 查看本机构的预约列表，在接种完成后将预约状态更新为"已完成"，触发库存扣减 |

**机构环节的数据关联**：机构管理员创建 **班次** 时必须关联本机构的 **护士**；处理 **入库** 时必须关联 **疫苗** 和 **生产商**；用户的 **预约** 必须关联本机构的 **班次**，且该班次对应的 **疫苗库存** 数量必须充足。

---

### 角色 3：生产商（疫苗工业生产商）

生产商是疫苗的供应源头，负责提供疫苗产品信息和批次供货记录：

| 功能模块 | 功能说明 |
|---|---|
| 维护疫苗产品信息 | 录入本厂生产的疫苗品种信息，包括疫苗名称、类型（如灭活/减毒/mRNA）、适用疾病、接种剂次、储存温度要求等 |
| 管理批次生产记录 | 记录每一批次疫苗的生产日期、批次编号、有效期、生产数量，作为供货和追溯的源头数据 |
| 管理供货配送记录 | 记录向各接种机构配送疫苗的情况，包括目标机构、疫苗品种、批次号、配送数量、配送日期，机构凭此记录进行入库确认 |

**生产商环节的数据关联**：生产商生产的每一 **批次疫苗** 都有唯一批次号；每次 **供货** 都关联具体的 **疫苗品种**、**批次** 和 **目标接种机构**；机构入库后，该批次疫苗的库存增加，形成 **生产商 → 供货记录 → 机构库存** 的完整链路。

## 三、数据要求

### 核心数据业务流程

系统的数据流转遵循以下链路：

```text
生产商生产疫苗（记录批次）
        ↓
生产商向机构供货（供货记录关联疫苗 + 批次 + 机构）
        ↓
机构入库确认（疫苗库存增加，关联疫苗 + 批次 + 机构）
        ↓
用户选择预约（选择疫苗 + 机构 + 护士班次，校验库存）
        ↓
机构确认接种（预约完成，库存扣减，生成接种记录）
```

| shift_date | DATE | NOT NULL | 班次日期 |
| start_time | TIME | NOT NULL | 开始时间（如 08:00） |
| end_time | TIME | NOT NULL | 结束时间（如 12:00） |
| max_appointments | INT | NOT NULL | 该班次最大可预约人数 |
| current_count | INT | NOT NULL, DEFAULT 0 | 当前已预约人数 |

#### 表 7：疫苗库存表（vaccine_stock）

存储接种机构中各疫苗的库存情况，按疫苗品种 + 机构 + 批次进行精细化管理。

| 字段名 | 数据类型 | 约束 | 说明 |
|---|---|---|---|
| stock_id | INT | PRIMARY KEY | 库存记录唯一标识 |
| institution_id | INT | FOREIGN KEY → institution | 所在机构（关联机构表） |
| vaccine_id | INT | FOREIGN KEY → vaccine | 疫苗品种（关联疫苗表） |
| manufacturer_id | INT | FOREIGN KEY → manufacturer | 生产商（关联生产商表） |
| batch_no | VARCHAR(50) | NOT NULL | 生产批次号 |
| quantity | INT | NOT NULL, DEFAULT 0 | 当前可用库存数量（不含已锁定） |
| locked_quantity | INT | NOT NULL, DEFAULT 0 | 已锁定数量（被预约占用，待扣减） |
| production_date | DATE | NOT NULL | 生产日期 |
| expiry_date | DATE | NOT NULL | 有效期（FEFO 出库排序依据） |
| storage_location | VARCHAR(100) |  | 储存位置（如冷库 A 区 3 号柜） |
| status | TINYINT | NOT NULL, DEFAULT 1 | 状态（1 正常 / 2 临期预警 / 3 已过期锁定 / 4 已销毁） |
| create_time | DATETIME | NOT NULL | 入库时间 |

**关联说明**：

- institution_id + vaccine_id 确定某机构中某疫苗的库存；
- manufacturer_id 和 batch_no 记录该批库存的来源生产商和批次，实现追溯；
- locked_quantity 记录已被预约锁定但尚未扣减的数量，quantity 仅为可用量；
- expiry_date 是近效期优先出库（FEFO）的排序依据；
- 用户预约时，系统需检查目标机构中该疫苗的 quantity > 0 且 status = 1。

#### 表 8：预约记录表（appointment）

| institution_id | INT | FOREIGN KEY → institution | 接种机构（关联机构表） |
| shift_id | INT | FOREIGN KEY → shift | 选择的班次（关联班次表） |
| stock_id | INT | FOREIGN KEY → vaccine_stock | 使用的库存批次（关联库存表） |
| appointment_date | DATE | NOT NULL | 预约接种日期 |
| status | TINYINT | NOT NULL, DEFAULT 1 | 状态（1 待接种 / 2 已完成 / 3 已取消） |
| create_time | DATETIME | NOT NULL | 预约时间 |

**关联说明**：

- user_id 关联用户表 —— 谁预约的；

- institution_id 关联机构表 —— 在哪个机构接种；

## 四、数据关联关系总览

以下梳理各表之间的核心数据关联，体现系统的完整数据链路：

```text
┌─────────────┐
│ manufacturer │  生产商
└──────┬──────┘
       │ 1:N
       ▼
┌─────────────┐         ┌──────────────┐
│   vaccine    │◄────────│ vaccine_stock │  疫苗库存
└──────┬──────┘   1:N   └──────┬───────┘
       │ 1:N                   │ N:1
       │                       ▼
       │                ┌──────────────┐
       │                │ institution  │  接种机构
       │                └──────┬───────┘
       │                       │ 1:N
       │                       ▼
       │                ┌──────────────┐
       │                │    nurse     │  护士
       │                └──────┬───────┘
       │                       │ 1:N
       │                       ▼
       │                ┌──────────────┐
       │                │    shift     │  护士班次
       │                └──────┬───────┘
       │                       │ 1:N
       ▼                       ▼
┌─────────────────────────────────────┐
│           appointment               │  预约记录
│  (user + vaccine + institution      │
│   + shift + stock)                  │
└──────────────┬──────────────────────┘
               │ N:1
               ▼
        ┌─────────────┐
        │    user     │  接种用户
        └─────────────┘
```

### 关键数据关联说明

| 关联路径 | 说明 |
|---|---|
| manufacturer → vaccine | 一个生产商可生产多种疫苗，每种疫苗归属于一个生产商 |
| manufacturer → vaccine_stock | 库存记录中标明该批疫苗来自哪个生产商，实现来源追溯 |
| vaccine → vaccine_stock | 一种疫苗在同一个机构可有多批次库存，按批次精细化管理 |
| institution → nurse | 一个机构拥有多名护士，护士隶属于机构 |
| institution → vaccine_stock | 一个机构存储多种疫苗的多个批次 |
| nurse → shift | 一名护士可有多个班次安排 |
| shift → appointment | 一个班次可被多个用户预约（不超过最大人数限制） |
| vaccine_stock → appointment | 预约时锁定某一批次的库存，接种后扣减该批次数量 |
| user → appointment | 一个用户可有多条预约记录 |

### 全链路追溯路径

```text
生产商(manufacturer)
  → 生产疫苗(vaccine)
    → 配送至机构，形成库存(vaccine_stock)
      → 用户选择疫苗 + 机构 + 班次，提交预约(appointment)
        → 预约完成，库存扣减
```

通过上述 8 张表的关联关系，系统实现了从 **生产商** 到 **接种用户** 的完整数据追溯链路，确保每一支疫苗的流向清晰可查。

## 五、核心数据操作规则

本节详细说明系统在日常运行和核心业务流程中涉及的关键数据操作规则，确保疫苗库存的安全性、时效性和可追溯性。

### 5.1 近效期优先出库（FEFO）

系统采用 **FEFO（First Expiry First Out）** 策略：当用户预约某机构的某种疫苗时，系统自动从该机构所有可用批次中，选择 **有效期最早** 的批次进行出库，确保临期疫苗优先被使用，减少过期浪费。

**操作规则**：

用户预约疫苗时，系统执行以下查询：

```sql
SELECT stock_id, batch_no, quantity, expiry_date
FROM vaccine_stock
WHERE institution_id = {目标机构}
  AND vaccine_id = {目标疫苗}
  AND status = 1              -- 仅选择状态为"正常"的批次
  AND quantity > 0            -- 仅选择有可用库存的批次
ORDER BY expiry_date ASC      -- 按有效期升序排列，最近的优先出库
LIMIT 1;
```

**示例场景**：

某机构存储了同一疫苗的 3 个批次：

| 批次号 | 可用数量 | 有效期 | 状态 |
|---|---|---|---|
| BN-2025-001 | 20 支 | 2026-11-15 | 正常 |
| BN-2025-003 | 15 支 | 2027-03-20 | 正常 |
| BN-2025-005 | 30 支 | 2027-08-01 | 正常 |

用户预约 1 支该疫苗时，系统自动选择 **BN-2025-001**（有效期 2026-11-15 最早）进行锁定和出库。

---

### 5.2 过期疫苗自动封锁

系统通过定时任务（每日凌晨执行）扫描所有库存记录，根据有效期自动更新状态，实现过期疫苗的实时封锁。

**状态流转规则**：

```text
┌──────────┐    距有效期 ≤ 30 天    ┌──────────┐    超过有效期    ┌──────────────┐
│  1 正常   │ ──────────────────→  │ 2 临期预警 │ ─────────────→  │ 3 已过期锁定  │
└──────────┘                      └──────────┘                 └──────┬───────┘
                                                                     │
                                                              管理员确认销毁
                                                                     ↓
                                                              ┌──────────────┐
                                                              │  4 已销毁    │
                                                              └──────────────┘
```

**操作规则**：

| 触发条件 | 系统操作 | 说明 |
|---|---|---|
| expiry_date - 当前日期 ≤ 30 天 且 status = 1 | 将 status 更新为 2（临期预警） | 提醒机构管理员优先使用，系统仍允许该批次出库 |
| expiry_date < 当前日期 且 status ∈ {1, 2} | 将 status 更新为 3（已过期锁定） | 立即禁止该批次参与任何预约和出库操作 |
| 管理员对 status = 3 的批次执行销毁操作 | 将 status 更新为 4（已销毁），quantity 置为 0 | 销毁记录保留，确保追溯链完整 |

**封锁约束**：

- status = 3（已过期锁定）的批次 **不可被 FEFO 查询选中**，不可被预约，不可出库；
- 若已过期批次存在 locked_quantity > 0（已被预约锁定但尚未接种），系统需 **自动释放锁定**（locked_quantity 置为 0），并将关联的预约记录状态更新为"已取消"，通知用户重新预约；
- 已销毁的批次记录 **不物理删除**，保留完整的库存历史以供追溯审计。

---

### 5.3 预约时的库存锁定与扣减

用户预约时，系统对库存执行 **先锁定、后扣减** 的两阶段操作，防止超卖和数据不一致。

**阶段一：预约锁定（用户提交预约时）**

1. 通过 FEFO 规则找到目标批次（status = 1, quantity > 0, expiry_date 最早）
2. 校验该批次的 quantity ≥ 1（可用库存充足）
3. 执行更新：

```sql
   UPDATE vaccine_stock
   SET quantity = quantity - 1,
       locked_quantity = locked_quantity + 1
   WHERE stock_id = {选中批次}
```

4. 创建预约记录（appointment），status = 1（待接种），stock_id 指向该批次

**阶段二：确认扣减（机构管理员确认接种完成时）**

1. 校验预约记录 status = 1（待接种）
2. 执行更新：

```sql
   UPDATE vaccine_stock
   SET locked_quantity = locked_quantity - 1
   WHERE stock_id = {预约关联批次}
```

3. 更新预约记录 status = 2（已完成）

**取消预约时的库存释放**：

1. 校验预约记录 status = 1（待接种）
2. 执行更新：

```sql
   UPDATE vaccine_stock
   SET quantity = quantity + 1,
       locked_quantity = locked_quantity - 1
   WHERE stock_id = {预约关联批次}
```

3. 更新预约记录 status = 3（已取消）

**关键约束**：quantity 始终表示实际可用量，locked_quantity 表示已被预约占用但尚未接种的量。两者之和等于该批次的实际物理库存总量。

---

### 5.4 临期预警与低库存预警

系统为机构管理员提供两类自动预警，辅助库存管理决策。

**临期预警**：

| 预警级别 | 触发条件 | 系统行为 |
|---|---|---|
| 黄色预警 | expiry_date - 当前日期 ≤ 30 天 且 status = 1 | 自动将 status 更新为 2，在机构管理端标黄显示，提示优先使用 |
| 红色封锁 | expiry_date < 当前日期 | 自动将 status 更新为 3，禁止出库，通知管理员处理 |

**低库存预警**：

| 预警条件 | 系统行为 |
|---|---|
| 某机构某疫苗的 所有正常批次 的 quantity 合计 ≤ 10 支 | 在机构管理端弹出低库存提示，建议联系生产商补货 |
| 某机构某疫苗 无任何正常批次库存（全部过期或数量为零） | 在前端用户查询页面隐藏该机构的该疫苗选项，避免用户选择后无法预约 |

### 5.5 数据操作规则汇总

以下汇总各操作场景下涉及的数据变更，确保规则清晰、无遗漏：

| 操作场景 | 涉及表 | 核心数据变更 |
|---|---|---|
| 用户预约接种 | vaccine_stock, appointment | 库存 quantity - 1, locked_quantity + 1（FEFO 选批次）；新增预约记录 |
| 确认接种完成 | vaccine_stock, appointment | 库存 locked_quantity - 1；预约状态 → 已完成 |
| 用户取消预约 | vaccine_stock, appointment | 库存 quantity + 1, locked_quantity - 1；预约状态 → 已取消 |
| 每日定时扫描 | vaccine_stock | 临期批次 status → 2；过期批次 status → 3，释放锁定并取消关联预约 |
| 管理员销毁过期疫苗 | vaccine_stock | status → 4，quantity 置 0，记录保留 |
| 生产商供货入库 | vaccine_stock | 新增库存记录，status = 1，quantity = 入库数量 |
| 用户查询可预约机构 | vaccine_stock, institution | 筛选 status = 1 且 quantity > 0 的机构+疫苗组合 |
| 用户选择班次 | shift | 校验 current_count < max_appointments |

## 六、总结

本系统围绕 **"用户选疫苗 → 选机构 → 选班次"** 的核心流程，通过 8 张数据表的关联设计，实现了从疫苗生产商到接种用户的全链路追溯。在数据操作层面，系统采用 **FEFO 近效期优先出库** 策略减少过期浪费，通过 **过期自动封锁 + 临期预警** 机制保障接种安全，借助 **预约锁定-确认扣减** 的两阶段库存操作防止超卖，形成了一套功能完整、数据安全、操作规范的疫苗管理数据库系统。
